## この文書は何のためにあるか

「Instagramから来たお客さん」を、ある人は「IG」、ある人は「インスタ」、ある人は「SNS」と書きます。**表記がバラバラだと、機械は同じお客さんの流入元だと分かりません。** そうなると「Instagramでいくら儲かったか」が永久に計算できません。

そこで**呼び方を先に固定します。** ここに書いてある値以外は使いません。コードもスプレッドシートもこの表を正本とします。

**変更したいときは、必ずこの文書を先に直してから、コードとスプレッドシートを直します。** 逆順でやると本番の表を作り直すことになります。

## 1. 流入元コード（12種）— どこから来たお客さんか

スプレッドシートの列名: `流入元コード`

| コード | 日本語の意味 | 具体例 | 誰が入力するか |
|---|---|---|---|
| `existing_customer` | 過去のお客さん | 前に一度ケータリングを頼んでくれた会社 | スタッフ |
| `existing_network` | ゆうさんの人脈 | 知り合いの経営者、前職の同僚 | スタッフ |
| `own_business` | 自社の他の事業のお客さん | TACHINOMIYA・サロン・火鍋のお客さん | スタッフ |
| `partner_space` | レンタルスペース経由 | 提携したレンタルスペースの紹介 | 自動（UTM） |
| `partner_bar` | BAR・クラブ経由 | 提携BARが1次会でうちを使った | 自動（UTM） |
| `partner_wedding` | 結婚式二次会会場経由 | 提携した二次会会場の紹介 | 自動（UTM） |
| `google_business` | Googleマップ・Google検索の店舗情報 | Googleビジネスプロフィールの投稿から | 自動（UTM） |
| `instagram` | Instagram | プロフィールリンク・ストーリー・DM | 自動（UTM） |
| `line` | LINE公式アカウント | LINE配信のリンクから | 自動（UTM） |
| `referral` | 紹介 | お客さんが友達を紹介してくれた | スタッフ |
| `organic_search` | 検索から自然流入 | 「沖縄 ケータリング」で検索して来た | 自動（UTM） |
| `other` | 上のどれでもない・不明 | 判別できないもの、過去データの埋め戻し | 既定値 |

**ルール**
- この12個以外の値は入れてはいけない。
- 迷ったら `other` にする。**空欄にはしない**（空欄は「未入力」と「該当なし」の区別がつかず集計が壊れる）。
- 「自動（UTM）」の行は、お客さんがクリックしたリンクから機械が判定するので**手入力しない**。

### 既存の `経路` 列との関係（大事）

`02_問い合わせ` シートには**すでに `経路` という列があります**。ここは自由記述で、これまでスタッフが好きに書いてきました。

- `経路`（既存・自由記述）→ **消さない。そのまま残す。** 人が読むメモとして使う。
- `流入元コード`（新規）→ **機械が集計するための正本。** 上の12値のみ。

過去データの移し替えは、次の対応表で機械的に行います。当てはまらないものは `other` に寄せます。

| `経路` に書かれていた文字（部分一致・大小文字無視） | → `流入元コード` |
|---|---|
| 紹介 / 口コミ / 知人紹介 | `referral` |
| リピート / 既存 / 前回 / 再依頼 | `existing_customer` |
| 知り合い / 人脈 / 直接 | `existing_network` |
| インスタ / instagram / ig / IG | `instagram` |
| LINE / ライン | `line` |
| Google / グーグル / マップ / MEO | `google_business` |
| 検索 / SEO / HP / ホームページ | `organic_search` |
| 立ち飲み / TACHINOMIYA / サロン / 火鍋 / 自社 | `own_business` |
| スペース / 会場 | `partner_space` |
| BAR / バー / クラブ | `partner_bar` |
| 二次会 / ウェディング / 結婚式 | `partner_wedding` |
| （上記以外・空欄） | `other` |

## 2. ステータス（13種）— 相手がいまどの段階か

スプレッドシートの列名: `ステータス`

| コード | 日本語の意味 | この状態の相手に何をするか |
|---|---|---|
| `NEW` | 登録したばかり | 連絡先が揃っているか確認する |
| `READY_TO_CONTACT` | 連絡する準備ができた | 今日〜数日で初回連絡する |
| `CONTACTED` | 初回連絡した | 3日待つ |
| `FOLLOW_UP_1` | 1回目のフォローをした | さらに4日待つ（初回から7日） |
| `FOLLOW_UP_2` | 2回目のフォローをした | 返事がなければ `DORMANT` へ |
| `REPLIED` | 返事が来た | **最優先で対応する** |
| `MEETING` | 打ち合わせ・商談になった | 提案・見積の準備 |
| `PARTNER_LISTED` | 提携先として掲載された | 30日後に問い合わせが来たか確認 |
| `INQUIRY` | 問い合わせが発生した | `02_問い合わせ` に行を作る |
| `QUOTED` | 見積を出した | 48時間後に追いかける |
| `WON` | 受注した🎉 | 口コミ依頼・紹介依頼・事例化 |
| `LOST` | 失注した | 失注理由を記録して寝かせる |
| `DORMANT` | 反応がなく休眠 | 3ヶ月後に別の切り口で再アプローチ |

### 遷移ルール（どの状態から、どの状態へ進めるか）

```
NEW → READY_TO_CONTACT → CONTACTED → FOLLOW_UP_1 → FOLLOW_UP_2 → DORMANT
                              │            │            │
                              └────────────┴────────────┴──→ REPLIED → MEETING
                                                                          │
                                              PARTNER_LISTED ←────────────┤
                                                    │                     │
                                                    └──→ INQUIRY → QUOTED → WON
                                                                     │       │
                                                                     └──→ LOST
```

**ルール**
- `REPLIED` はどの段階からでも入れる（相手はいつ返事してくるか分からない）。
- `DORMANT` からは `READY_TO_CONTACT` に戻せる（再アプローチ）。
- `WON` と `LOST` からは戻さない。追加受注は**新しい行**として登録する（1行=1商談）。
- 上の図にない飛び越しは、機械が**警告を出す**（止めはしない。現場が実態に合わせて直せるようにする）。

### 既存の4列との関係

`CATERING_SALES_TARGETS` には**すでに `返信状況` `商談状況` `見積状況` `成約状況` の4列があります**。

- 既存4列 → **消さない。そのまま残す。**
- `ステータス`（新規）→ **13値の正本。** 既存4列から機械的に導出できる。

導出ルール（上から順に判定し、最初に当たったものを採用）:

| 条件 | → `ステータス` |
|---|---|
| `成約状況` が「成約」「受注」 | `WON` |
| `成約状況` が「失注」 | `LOST` |
| `見積状況` が「提出済」 | `QUOTED` |
| `商談状況` が「商談中」「打合せ」 | `MEETING` |
| `返信状況` が「返信あり」 | `REPLIED` |
| `初回アプローチ日` があり、最終接触から7日超 | `FOLLOW_UP_2` |
| `初回アプローチ日` があり、最終接触から3日超 | `FOLLOW_UP_1` |
| `初回アプローチ日` がある | `CONTACTED` |
| 連絡先（電話・メール・Instagramのいずれか）がある | `READY_TO_CONTACT` |
| 上記以外 | `NEW` |

## 4. UTM の命名規則 — お客さんがどこから来たか自動で分かる仕組み

### UTM とは（1行で）

**リンクの後ろに「どこから来たか」の目印を付ける仕組みです。** `https://例.com/?utm_source=instagram` のようにすると、Instagramに貼ったリンクから来た人だと後で分かります。Googleが決めた世界共通のやり方なので、**無料で、追加ツールも不要です**。

### 4つのパラメータの決め方

| パラメータ | 入れる値 | 例 |
|---|---|---|
| `utm_source` | **流入元コード（§1の12値そのまま）** | `instagram` |
| `utm_medium` | チャネル（下表の9値） | `story` |
| `utm_campaign` | `tc_<年月>_<用途>` | `tc_202608_partner_open` |
| `utm_content` | **対象先ID** または **テンプレートID** | `tc_0042` |

`utm_medium` に使える値（9種）:

| コード | 意味 |
|---|---|
| `line` | LINEのメッセージ |
| `dm` | Instagram/ThreadsのDM |
| `email` | メール |
| `story` | Instagramストーリー |
| `feed` | Instagramフィード投稿 |
| `gbp_post` | Googleビジネスプロフィールの投稿 |
| `qr` | 印刷物のQRコード |
| `referral_card` | 紹介カード（紙） |
| `organic` | 自然流入（自分で貼っていないもの） |

### 書き方のルール（絶対）

- **小文字の英数字とアンダースコア（`_`）だけ。**
- **日本語・空白・大文字は禁止。** リンクが壊れて流入元が追えなくなる。
- 機械がこれを検査して、違反した値は**受け付けずエラーを返す**。

✅ OK: `partner_space` `instagram_story` `tc_202608_past_customer`
❌ NG: `パートナー` `Instagram Story` `partner-space`（ハイフン不可）

### 一番大事な設計 — 人にURLを手打ちさせない

**UTM付きURLは、対象先IDから機械が自動で作ります。** スタッフはコピーするだけ。

理由: 手打ちさせると必ずタイプミスが起きます。1文字違うだけでその売上は「不明な流入元」に落ち、**どの施策が儲かったのか分からなくなります**。せっかく作った仕組みが数字を出さなくなる、一番ありがちな失敗です。

LPのURL本体は**コードに直接書きません**。環境変数 `CATERING_LP_BASE_URL`（無ければ `configs/business_registry.py` の `booking_url`）から読みます。LPのURLが変わっても、コードを直さずに済みます。

## 5. ID の付け方

| ID | 形式 | 例 | どこで採番 |
|---|---|---|---|
| 対象先ID | `tc_` + 4桁連番 | `tc_0042` | `CATERING_SALES_TARGETS` に登録時 |
| 問い合わせID | `inq_` + 年月 + `_` + 3桁連番 | `inq_202608_007` | `02_問い合わせ` に行を作る時 |
| テンプレートID | `tpl_` + 用途 | `tpl_partner_space_01` | `TEMPLATE_LIBRARY` に登録時 |

**ルール**: 一度振ったIDは**絶対に変えない・使い回さない**。行を消す場合もIDは欠番にする（過去の売上との紐付けが切れるため）。

## 6. 失注理由（8種）— なぜ negatively 終わったか

スプレッドシートの列名: `失注理由`

| コード | 意味 | 打ち手のヒント |
|---|---|---|
| `price` | 予算が合わなかった | 低単価オードブル商品を出す |
| `date_unavailable` | 日程が埋まっていた | 提携先に流す／人員体制 |
| `menu_mismatch` | 料理内容が希望と違った | メニュー幅を増やす |
| `headcount` | 人数が対応範囲外 | 最小/最大人数の見直し |
| `competitor` | 他社に決まった | 差別化（設営・撤収込み）を前面に |
| `internal_cancel` | 相手側の都合で企画が消えた | 追いかけ不要。次回に寝かせる |
| `no_response` | 途中で連絡が途絶えた | フォロー回数・タイミングの見直し |
| `other` | その他 | メモに詳細を書く |

**なぜ必要か**: 失注理由が `price` ばかりなら**値段の問題**、`date_unavailable` ばかりなら**キャパの問題**です。打ち手が正反対になるので、ここを記録しないと改善が当てずっぽうになります。

## 7. 優先度（3段階）

スプレッドシートの列名: `優先度`（既存列）

| 値 | 意味 | 判定の目安 |
|---|---|---|
| `A` | 今週動く | 想定単価が高い or 決定権者に直接つながる or 返事が来ている |
| `B` | 今月中に動く | 見込みはあるが急がない |
| `C` | 余力があれば | 単価が低い or 関係が薄い |

`見込み確度`（0〜100の数値）は別列で持ちます。優先度は**行動の優先順**、見込み確度は**受注する確率**で、別のものです。

## 8. この文書を変更するときの手順

1. **この文書を直す**（`docs/` だけなので低リスク＝自動マージ可）
2. `sheet-schema.md` に影響があれば直す
3. `configs/catering_growth_vocab.py`（コード側の定数）を直す
4. テストを直す
5. スプレッドシートの列を直す（**オーナー承認必須**・版履歴で復元ポイントを作ってから）

**この順番を逆にしないこと。** 先にスプレッドシートを触ると、あとから呼び方を変えたくなったときに本番の表を作り直すことになります。
