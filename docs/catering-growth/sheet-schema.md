## 0. この設計の考え方（3行）

1. **新しいスプレッドシートは作りません。** TREE's Catering の既存ワークブック（`CATERING_SPREADSHEET_ID`）の中だけで完結させます。
2. **既存の列は1つも動かしません。** 追加は**常に表の右端**。並べ替え・改名・削除は禁止です。
3. **新しいシートは2枚だけ。** それ以外は既存シートへの列追加で足ります。

### なぜ「右端に追加だけ」なのか（重要）

既存のプログラム `core/catering_report.py` は、表を**列の位置（左から何番目か）で読んでいます**（`r[4]` のような書き方）。

つまり、**表の途中に列を1本入れると、その右にある全部の列が1つズレて、プログラムが違う値を読み始めます。** 週次レポートの受注率や粗利率が静かに間違った数字になる、という最悪の壊れ方をします。

**右端に足すだけなら、左から数えた位置は何も変わらないので安全です。** これがこの設計の絶対ルールです。

## 1. いま何が足りないのか — 「粗利が追えない」の正体

TREE's Catering のワークブックには、すでに問い合わせから利益までの表が揃っています。ところが**表と表をつなぐ「共通の番号」がありません。**

### 現状（つながっていない）

```
CATERING_SALES_TARGETS （営業先リスト）
        ✗ つながっていない
02_問い合わせ          … 番号の列が無い
        ✗ つながっていない
03_見積                … 見積番号はあるが、どの問い合わせの見積か不明
        ✗ つながっていない
04_受注管理            … 受注番号はあるが、どの見積の受注か不明
        ✔ 受注番号でつながっている
06_売上管理 / 07_利益管理
```

**結果**: 「Instagram経由のお客さんが、合計いくら受注して、いくら粗利が出たか」が計算できません。仕様書が一番大事だと言っている数字が、いまは出せない状態です。

### 修正後（つながる）

```
CATERING_SALES_TARGETS（対象先ID: tc_0042 / 流入元コード: instagram）
        ↓ 対象先ID
02_問い合わせ（問い合わせID: inq_202608_007 / 流入元コード: instagram）
        ↓ 問い合わせID
03_見積（見積金額 / 粗利）
        ↓ 問い合わせID・見積番号
04_受注管理（受注番号 / 受注金額 / 粗利）
        ↓ 受注番号（← 既にある）
06_売上管理（売上金額） / 07_利益管理（粗利・粗利率）
```

**足すのは「番号の列」だけ。** これだけで流入元 × 受注 × 売上 × 粗利がつながります。

## 4. 数字の正本をどこに置くか（迷いをなくすルール）

同じ「粗利」が複数の表にあるので、**どれを信じるかを先に決めます**。決めないと、レポートによって数字が違うという最悪の状態になります。

| 数字 | 正本（第1候補） | 代わり（第2候補） | ルール |
|---|---|---|---|
| 粗利 | `07_利益管理.粗利` | `04_受注管理.粗利` | 第2候補を使ったときは `粗利の出典` 列に記録する |
| 売上 | `06_売上管理.売上金額` | `04_受注管理.受注金額` | 同上 |
| 受注の有無 | `04_受注管理.受注状況 = "受注"` | — | 既存プログラムと同じ判定を使う |
| 流入元 | `02_問い合わせ.流入元コード` | `CATERING_SALES_TARGETS.流入元コード` | 問い合わせ側が優先（最終接触の実態に近い） |

### 「結合できなかった件数」を必ず表示する理由

番号が入っていない古いデータは、流入元と紐付けられません。こういう行を**黙って捨てると「Instagram経由の売上は50万円」と表示されるが、実は集計対象外が200万円ある**という事故が起きます。

なので **紐付けできなかった件数と金額を必ず画面に出します。** 「今回集計できたのは全体の何割か」が分かる状態にします。

## 5. 列を追加する手順（マイグレーション）

この仕組みにはデータベースがありません。**列を足す道具も無いので、作ります。**

```
ensure_columns(ss, シート名, 欲しい列名リスト, dry_run=True)

  1. いまのヘッダ行を読む
  2. 足りない列だけを洗い出す
  3. dry_run=True（既定） → 「これを足す予定です」と報告するだけ。1マスも書かない
  4. dry_run=False       → 右端にだけ追加する
  5. 何度実行しても結果が同じ（2回目は「足すものなし」になる）
```

**この関数には「途中に挿入する」「名前を変える」「削除する」機能を作りません。** 機能が無ければ事故も起きません。

### 実行の順番（絶対に守る）

1. **オーナーがスプレッドシートの版履歴で復元ポイントを作る**（`ファイル > 版履歴 > 現在の版に名前を付ける`）
2. `dry_run` で実行 → 「何を足すか」の一覧をオーナーが確認
3. **オーナーが承認**
4. `?dry_run=0` を明示して実行
5. **確認テスト**: `/catering-weekly` を叩いて、**受注率・粗利率が列追加前と同じ数字になることを確認**。1つでも変わっていたら列がズレている ⇒ 版履歴から戻す

### 実際のエンドポイント（2026-07-27 実装済 / W1-6）

| 用途 | エンドポイント | 既定 |
|---|---|---|
| CRM シート作成（33列） | `/catering-sales-setup` | **書き込む**（`?dry_run=1` で確認のみ） |
| 結合キー列の追加 | `/catering-funnel-keys` | **dry-run**（`?dry_run=0` で適用） |
| 既存行への番号の埋め戻し | `/catering-backfill-inquiry-ids` | **dry-run**（`?dry_run=0` で適用） |
| UTM 付き URL の生成 | `/catering-utm?source=…&medium=…&campaign=…&content=…` | 読み取りのみ |

> `/catering-sales-setup` だけ既定が「書き込む」なのは、W1-2 以前から存在する
> エンドポイントで既存の挙動を変えないため。新規の2本は**dry-run 既定**にしている。

### ⚠️ `core/catering_setup.py` は二度と実行しない

このプログラムは `sh.update("A2:O2", …)` でヘッダ行を**上書き**します。データが入った本番シートに走らせると、**追加した列が消えます。** 実行禁止をSOPに明記します。表の変更は `ensure_columns` だけを使います。

### 古いデータへの番号の埋め戻し

既存の `02_問い合わせ` の行には `問い合わせID` がありません。以下のルールで後から埋めます。

- ID: `inq_` + その行の `問い合わせ日` の年月 + `_` + 3桁連番
- `流入元コード`: `vocabulary.md` §1 の対応表で `経路` から機械変換。当たらなければ `other`
- **空欄のマスだけを埋めます。すでに値が入っているマスは絶対に上書きしません。**
- これも dry_run → 承認 → 実行の2段階

## 8. 何ができるようになるか（この設計のゴール）

| いまできないこと | 設計後にできること |
|---|---|
| Instagram経由の売上がいくらか分からない | 流入元12種類別に 受注数・売上・粗利が出る |
| どの営業文が効いたか分からない | テンプレ別の返信率と**受注粗利合計**が出る |
| 提携先が機能しているか分からない | 掲載30日で問い合わせゼロの提携先が自動で挙がる |
| 100件の連絡先を手入力するしかない | CSVで一括投入できる |
| 誰に今日連絡すべきか分からない | 8つのルールで自動抽出し、既存のLINE配信に乗る |
| 失注の理由が集計できない | 8分類で集計 → 値段の問題かキャパの問題か分かる |
| ゆうさんが毎回文章を作っている | テンプレ＋差し込みで完成文が出る。ゆうさんは承認だけ |
